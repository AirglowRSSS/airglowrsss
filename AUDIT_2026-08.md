### Stage 5: `wave_validation.py`

**What changed since baseline:**
1. **Voronoi tolerance: documented 2× → actual 1×.** Baseline Section 3 states "Groups
   are defined by 2×DIR_TOL_DEG and 2×LAMBDA_TOL_KM." Current code
   (`gabor_reconstruction.py:605-615`, `build_waves_for_gabor`'s `voronoi_dir_tol`/
   `voronoi_lam_tol` parameters) defaults to **1×** `dir_tol_deg`/`lambda_tol_km`, with an
   explicit code comment: *"The old behaviour was `2*dir_tol_deg` which caused transitive
   over-grouping when three or more families lined up incrementally in direction or
   wavelength space."* This is a **documented, intentional bug fix**, not undocumented
   drift — but it directly contradicts the baseline's Section 3 claim, which was written
   describing the old (2×) behavior as a design decision "not to reverse without
   discussion." Flagging this explicitly since the baseline text is now wrong on this
   point, even though the change itself looks well-justified.
2. **Family-grouping half-circle-only clustering bug (found and fixed today).**
   `build_wave_families`'s greedy grouping compared only the half-circle axis
   (`_angular_diff`, wraps every 180°) between a candidate detection and a group's founding
   centroid, never checking the full-circle `azimuth_full`. Two detections whose axes
   wrapped close together near the 0°/180° boundary (e.g. 14° and 175°) but whose true
   propagation directions differed by ~160° could merge into one family. Fixed today by
   also requiring `azimuth_full` proximity. This directly caused a real, user-confirmed
   problem: a family that was actually two physically distinct waves (see deep dive
   below).

**Founding-centroid behavior itself (baseline's core Section 3 claim) still holds** — the
group's `direction_center`/`wavelength_center` (now also `azimuth_full_center`) are still
fixed at the founding detection and never updated, exactly as documented, with the same
stated rationale (prevent drift-chaining).

**Status:** Confirmed working post-fix; the pre-fix clustering bug was real, reproducible,
and visually confirmed against a specific night's data (DOY 173 2023, LOW site) before
being fixed.

### `cluster_reconstruction.py` / `coordinate_conversion_adapter.py`

Not separately called out in the baseline's per-stage table, but load-bearing for every
Gabor kernel build, and the source of the single highest-impact bug found this session:

`coordinate_conversion_adapter.convert_angle()` wrapped negative results back into
`[0, 180)`, creating a genuine discontinuity exactly at `orientation_deg = 90°`
(`convert_angle(89.99°) ≈ 0°` vs. `convert_angle(90.01°) ≈ 180°`). Since this feeds
`theta_rad` directly into `create_gabor_kernel`'s `cos`/`sin` calls, it flipped the kernel
to its complex conjugate — inverting the sign of `kf_omega_rads` — for any wave whose
`orientation_deg` exceeded 90°. Verified against a synthetic wave of known ground-truth
direction, tested across all four quadrants, using the actual deployed
`create_gabor_kernel` (not a hand-copied replica — an earlier verification pass this
session used a replica and incorrectly concluded the fix was working end-to-end when it
hadn't yet been re-tested against the real function). The module's own docstring
contained a second, related problem: it described "Convention B" as "0°=North,
90°=**West**" (counterclockwise), contradicting `phase_speed_kalman.py`'s documented and
actually-used "0°=North, 90°=East, clockwise." This mismatched comment is the likely
historical origin of the clamp bug, though the fix required did not need a handedness
change — only removing the unnecessary wrap. Both are fixed as of `1b4e95d`.

**Category:** Bug fix. **Status:** Confirmed working, verified against the real function,
not a synthetic-only check.

## Deep-dive: wave deduplication / merging across drift

**Where it lives, and whether it's one coherent pass or scattered:** It is **two
genuinely separate mechanisms**, not one pass, and they address different failure modes:

1. **`build_wave_families()` in `wave_validation.py`** — the founding-centroid greedy
   clustering that groups *raw per-window ω-k detections* into families. This decides
   whether two detections *at different times* are the same physical wave based on
   parameter proximity to a fixed founding centroid. As of today's fix, the match
   condition (line ~329-346) requires **all three**: `_angular_diff(direction, axis) <
   dir_tol_deg` (half-circle axis distance), `_full_circle_diff(azimuth_full,
   azimuth_full_center) < dir_tol_deg` (full-circle direction distance, added today), and
   `abs(wavelength - wavelength_center) < lambda_tol_km`. With current notebook config,
   `dir_tol_deg = 22.5°`, `lambda_tol_km = 20.0` km.

2. **Voronoi tie-break within wave groups, in `build_waves_for_gabor()` /
   `gabor_reconstruction.py`** — a *separate* pass that groups **families** (not raw
   detections) that are close enough to represent one physical wave whose parameters
   drifted enough to be split into multiple families by (1). Match condition: family pairs
   within `voronoi_dir_tol` (default `dir_tol_deg`, i.e. 1×, see above) on
   `_angular_diff(direction_center, direction_center)` **and** `voronoi_lam_tol` (default
   `lambda_tol_km`, 1×) on wavelength center difference — grouped via union-find
   (transitive). Within such a group, per-frame ownership of contested frames goes to
   whichever family's nearest detection centre is closest in time (not amplitude, not
   confidence).

3. **`flag_kf_wave_collisions_by_correlation()` in `phase_speed_kalman.py`** — a *third*,
   fully independent, much later-stage pass, operating not on detection parameters at all
   but on **pixel-level Pearson correlation of the actual second-pass reconstructed
   fields**, per frame, with a rolling-mean smoothing window (5 frames) and a
   correlation threshold of 0.7 (empirically calibrated — see docstring, "just above the
   observed p99 of ~0.68"). N-way collisions resolved via connected components; the
   surviving wave per episode is whichever has minimum average normalized distance to its
   own founding orientation/wavelength. This is the mechanism added in `63f5b4d` to
   replace an older, removed parameter-tolerance check.

**Do these interact or duplicate each other?** They operate at different pipeline stages
on different data (raw detections → families → second-pass reconstructed pixels) and are
not redundant with each other in the sense of re-deciding the same question — but they
**can and do produce related-looking symptoms if an earlier stage is wrong**, which is
exactly what happened this session: the (1) clustering bug meant one "family" was
genuinely two different waves; downstream, this manifested as a confusing, seemingly
direction-independent correlation between two *other*, distinct, correctly-separated
families whose Gabor kernels merely had overlapping angular passbands (an
axis-only-selective kernel cannot distinguish a wave's forward vs. backward propagation
direction from a single-frame real-valued snapshot — see the conventions deep-dive). The
(3) collision detector correctly flagged that correlation; the mistake this session was
initially assuming it was a bug in (3) rather than a legitimate consequence of kernel
geometry plus real, if oblique, spatial-frequency overlap between two genuinely different
waves. This was resolved (by the user's own physical judgment, not a code fix) as
**expected, not a bug**: correlation-based dedup on real-valued reconstructions cannot
distinguish a true 180°-direction ambiguity from two waves sharing an axis, and choosing
to merge on high correlation is the defensible default given how unlikely two distinct
wavefields propagating in near-opposite directions at the same place and time is
considered to be.

**Reactive/night-specific patching:** No conditional special-casing for specific nights
was found in the merge/collision code itself. The threshold values (0.7 correlation,
1× Voronoi tolerance) are both accompanied by code comments citing the reasoning
(percentile calibration; avoiding transitive over-grouping) rather than being tuned to a
specific night's numbers, though both were informed by real-data validation on the
DOY 173 2023 LOW-site case study used repeatedly this session — whether that
generalizes to other sites/nights has not been separately tested.

**Tests / synthetic validation of drift-driven merging specifically:** None found. All
validation this session (and, per commit messages, in prior sessions) was against real
MANGO imagery, visually and via residual-structure comparison, not a synthetic case
constructed to exercise a wave drifting from one family's parameter space into another's.
This is a real gap — the deep-dive's own framing (families beginning distinct and drifting
into a neighbor's territory) is exactly the scenario `build_waves_for_gabor`'s Voronoi
tie-break exists to handle, and it has never been exercised by a controlled synthetic
case with known ground truth.

## Deep-dive: orientation / propagation-direction conventions

**1. Compass azimuth (0–360°, 0°=N, 90°=E, clockwise).** Used for `wave['azimuth']`,
`kf_prop_azimuth_deg`, `kf_orient_deg`, `azimuth_full` throughout. Confirmed consistent
with the baseline and with `phase_speed_kalman.py`'s own docstring. The one contradicting
document was `coordinate_conversion_adapter.py`'s stale comment (fixed today).

**2. Gabor kernel orientation (0–180°, no forward/backward distinction).**
`orientation_deg`, `gabor_orientation_deg`, `direction` (in `build_wave_families`'s raw
detection dicts). Fed to `create_gabor_kernel` via `convert_angle()`.

**3. Propagation direction (0–360°, has a definite forward sense).** Recovered from (2)
via the **sign of `kf_omega_rads`** (or, upstream, the original ω-k detection's own
`arctan2(-kx, -ky)` on the omega-positive-only half of the FFT). This is the exact
conversion point the audit specifically calls out as bug-prone, and it was, twice, this
session:

- **Bug A (fixed):** `create_gabor_kernel` (via the buggy `convert_angle`) inverted this
  sign for any axis > 90°. File: `cluster_reconstruction.py` (kernel build) +
  `coordinate_conversion_adapter.py` (the actual bug). Fixed in `1b4e95d`.
- **Bug B (found, fixed, then the "fix" itself found unsafe and reverted):**
  `validate_wave_azimuth_sign()` was built on the premise that `kf_omega_rads`'s sign is a
  trustworthy ground truth for direction, and (for part of today's session) auto-corrected
  `wave['azimuth']` when it disagreed with the fixed ω-k azimuth. On real data, this
  **flipped an already-correct azimuth** (Family 1, DOY 173 2023 LOW — 345° visually
  confirmed correct, flipped to 165°). The mechanism turned out to be exactly what
  `_kalman_omega_tracker`'s own docstring already warns against: *"noise bursts that push
  the cross-correlation phasor across zero contaminate the sign estimate for many frames
  due to slow Kalman gain. Tracking |ω| eliminates all such artefacts."* That is also
  precisely why `kf_prop_azimuth_deg` has always been hard-fixed to the original ω-k
  azimuth regardless of `kf_omega_rads`'s sign — a design decision already present in the
  code before this session, that the now-reverted auto-correction logic effectively
  overrode. The tell that something was systematically wrong (not just noisy real data)
  was mechanical: every auto-"corrected" azimuth landed exactly on `orientation_deg`
  (always < 180°), never on `orientation_deg + 180`, which is not what genuine,
  evenly-distributed real-data sign disagreement should look like.

**Where 0–180° and 0–360° values get compared/differenced without reconciling
convention:** `validate_wave_azimuth_sign()` itself does this correctly (via
`circular_diff_deg` after taking both mod 360). I did not find an unreconciled
direct-comparison bug pattern elsewhere in the current code — the two closest calls
(`_kalman_theta_tracker`'s `kernel_mismatch` half-circle comparison, and the
Voronoi/clustering `_angular_diff`) both explicitly fold to half-circle space before
comparing, which is correct for those specific (axis, not direction) comparisons.　

**Doubled-angle interpolation** (see Section 4 checklist above): present and correct in
`interpolate_family_to_time_grid`; not needed/used elsewhere because other half-circle
handling in the codebase uses direct fold-to-nearest-reference logic
(`_kalman_theta_tracker`) rather than interpolation.

**Real-data cases where displayed direction disagreed with visually apparent motion, and
what the actual bug was (not just "fixed direction convention"):**
1. Two families that appeared to move in the same direction in the second-pass movie —
   root cause was the clustering bug (one "family" was genuinely two different waves);
   fixing the clustering separated them into two families whose real, distinct directions
   (~7-11° apart, not opposite) turned out to be genuinely similar, resolving the visual
   confusion without any azimuth-convention change at all.
2. A specific wave panel's velocity arrow pointing opposite the visually-apparent crest
   motion — root cause was Bug A above (the `convert_angle` discontinuity), confirmed via
   synthetic ground truth and fixed.
3. Family 1's azimuth being auto-flipped from a correct 345° to an incorrect 165° — root
   cause was Bug B above (trusting `kf_omega_rads`'s sign against the codebase's own prior
   design warning); fixed by reverting the auto-correction, not by changing any
   convention.

## Closure note (2026-08-18, post-audit follow-up)

The item flagged above as "the single largest open question" from this audit's Stage 4
detail section — nine of fourteen families flagged by `validate_wave_azimuth_sign` on
DOY 173 2023 LOW with no identified cause — is now resolved.

**Summary:** `kf_omega_rads` is architecturally always ≥ 0 (`analyze_all_waves_kalman`
takes `abs()` of both the per-frame observation and the initial state before the omega
Kalman filter runs, by original, pre-this-session design, to avoid noise-induced
sign-flip artefacts). It therefore cannot disagree with `wave['azimuth']` in the
informative direction, which made `validate_wave_azimuth_sign`'s flag rate a
deterministic function of whether a family's azimuth already equals `orientation_deg`
or `orientation_deg + 180°` — not a measurement of anything. A synthetic
ground-truth sweep (real, deployed functions, full 360° coverage) confirmed
`wave['azimuth']`/`identify_physical_waves` is correct across the entire circle, and
`validate_wave_azimuth_sign` has been removed entirely rather than fixed, since the
comparison it was built to make cannot be made from this signal.

Full diagnosis: `SIGN_DISAGREEMENT_INVESTIGATION.md` (real-data investigation, five
checked mechanisms, all ruled out) and `SIGN_DISAGREEMENT_SYNTHETIC_SWEEP.md` (the
synthetic sweep that isolated the exact root cause and corrected the first report's
leading hypothesis). `CLAUDE_original_2026-07-02.md` Section 3 has been updated to
record this as a standing design note.
